# 插件化、Android/iOS 与课表里程碑规划

规划版本：v1。产品范围已由用户确认；技术路线为待评审候选，不是冻结架构或实施完成记录。

入口：[M-EXT-01 与所属任务](../TODO.md#m-ext-01) · [D-EXT-001](../DECISIONS.md#d-ext-001)。任务状态只由主 TODO 维护。

## 1. 已决定的目标

用户应能在桌面、Android 和 iOS 使用基础笔记能力，安装遵循本产品协议的第三方插件，并通过课表插件导入、查看课程和设置提醒。手机端使用适合触屏的页面，不复制桌面置顶/壁纸层/托盘的交互。

- 首期真实支持第三方插件包安装，不以内部组件可注册替代。
- 手机覆盖 Android 和 iOS；可以依次开发，但两端都有验收才算移动目标达成。
- 首期手动导入导出；自动同步单独作为后续产品范围，不建立账号服务、后台同步或合并协议。
- 课表插件必须通过公开的宿主协议和正常安装路径工作，避免给内置课表安排绕过权限的特殊通道。

## 2. 当前基础与缺口

现有项目使用 Tauri 2 + SvelteKit + Rust。`src-tauri/src/lib.rs` 虽有 mobile_entry_point，但单实例/桌面模块/命令与 Cargo 依赖仍按桌面组织，不能把入口标记当作手机版已经就绪。

已有 `registerNoteTextCommand` / `registerNoteLineCommand`，见 [历史命令插件机制](../ui/2026-02-09-markdown-phase3-command-plugin-system.md)。它是 Markdown 命令扩展点，不包含第三方包安装、权限隔离、插件生命周期和跨端协议；可复用为一个扩展点，不能直接充当插件系统。

安全缺口优先于开放安装：当前 capabilities 用 `windows: ["*"]`，asset scope 为 `**`，CSP 未设置。不得把不受信任插件直接放入已有特权 WebView，也不得认为 JS 层包装函数本身就是权限隔离。

已有数据安全整改是共用基础：后端拥有笔记与偏好写入，草稿保护/原文校验与原子写入不被插件或导入路径绕开。此前平台验收缺口继续保留在原 Task，不被新里程碑自动关闭。

## 3. 候选架构与取舍

| 层 | 职责 | 不能由该层代替的保证 |
| --- | --- | --- |
| 宿主核心 | 受控笔记接口、插件数据空间、权限、导入事务、提醒计划管理 | 不能把插件传来的 pluginId 当可信身份 |
| 平台适配 | 桌面窗口能力；Android/iOS 文件选择、应用存储、通知与生命周期 | 同一函数签名不证明两端系统行为相同 |
| 插件运行层 | 安装包、版本兼容、启停、受限 UI/逻辑、异常与超时处理 | 不能只用 catch 或模块命名宣称安全沙箱 |
| 课表插件 | 课程规则、周视图/今日课程、导入校验和提醒配置 | 不直接覆盖核心 notes/preferences 文件，不自建常驻计时循环 |

建议先评估继续沿用 Tauri 的路线，因为已有业务逻辑与 Svelte 组件可复用；先用最小手机端到端路径证明外部包加载、存储和锁屏提醒，再决定完整迁移。该验证若发现关键能力或分发要求不能满足，才比较更换移动壳的收益与维护成本，不提前重写客户端。

第三方插件包候选包含 manifest、前端资源/受限逻辑、权限声明、宿主协议版本与支持平台、插件数据版本。manifest/package 的具体字段和运行时尚未冻结。

运行形态候选：隔离 Web 内容加受控消息桥，或表达力受限的声明式扩展；任意原生库/任意文件系统/直接 Tauri invoke 不作为首期默认能力。最终选择必须同时满足真实第三方功能、移动端隔离和目标分发渠道，不能用受限模板悄悄替换用户要求的插件能力。

首期安装管理应覆盖安装、升级、启停、权限变更提示和卸载。先支持可验证来源的插件包导入；在线商店/付费/作者后台是非当前阻塞项，只有实际分发需求出现才扩展。完整性校验与作者信任是不同证据，不把包内自带 hash 当作可信作者签名。

## 4. 课表 JSON 规范方向

仓库尚未发现课表 JSON 正式规范。若用户已有样例，先对齐样例再定字段；以下是需要承载的语义，不是已经通过验收的 schema。

| 数据组 | 需要覆盖的内容 | 缺失的后果 |
| --- | --- | --- |
| 格式身份 | schemaVersion、课表稳定 ID | 无法识别兼容版本与重复导入 |
| 学期 | 开始日期、周次计算规则、时区、有效范围 | 第几周、跨时区日期容易算错 |
| 节次 | 每节开始/结束时间与节次标识 | 相同“第3节”在不同学校不对应相同时间 |
| 课程 | 课程稳定 ID、名称、老师等描述 | 课程信息与每次上课安排混在一起 |
| 上课安排 | 独立安排 ID、课程引用、星期、周次集合、节次/时间和教室 | 同一课程多时段/教室无法表达 |
| 例外 | 指定日期停课、补课、调课 | 只靠单双周无法表达真实教学安排 |
| 提醒偏好 | 提前量、启停及作用范围 | 更新/导入后提醒规则无从重建 |

原始课表规则是可导出的业务数据；每台设备上的系统通知 ID/权限状态不是跨端可移植数据，导入后由各端重新调度。手动导出首期至少覆盖笔记正文与必要元数据、课表及其提醒设置、受允许的插件数据；不搬运凭据或直接复制整份运行目录。容器格式与现有 Markdown 导出如何组合在接口阶段确定。

课表 JSON 是插件的数据合同，不改变既有“笔记以 Markdown 互操作”的范围约定，也不宣称任意学校原始 JSON 都可直接兼容。学校爬取/OCR/账号登录属于后续适配器，不含在本次导入承诺中。

导入要求：先校验版本、类型、ID、课程引用、周次与节次，再显示新增/覆盖预览并提交；坏输入不能部分覆盖旧课表。重复导入相同 ID 不重复生成课程或提醒；有冲突的覆盖/合并规则在 schema 定稿时明确。

## 5. 提醒合同

插件提交课程事件与提醒计划，由宿主管理标识、平台调度、取消及重建。后台与锁屏提醒不能依赖桌面现有每 250ms 轮询/WebView 常驻；插件停用后，应取消它拥有的未来提醒但默认保留其数据；停课、调课、改提前量、重复导入均须清除陈旧提醒。

验收覆盖正常前台、后台、锁屏、系统终止后的支持行为、设备重启、时区变化和权限撤销；按平台实际保证和限制定义结果，不承诺在系统明确禁止通知或强制停止的条件下仍必达。拒绝权限时界面必须显示不可用原因，不能保存一个看似生效的开关。

## 6. 实施顺序建议

1. 跨端插件可行性验证：先验证外部包安装/受控调用和移动通知链；触发原因是 iOS 分发和后台机制可能反向约束插件协议，产出可选路线的真实证据，避免先做大宿主再返工。
2. 第三方插件宿主与 Android/iOS 基础客户端：依据验证结果确定共用接口和平台差异，分别完成各自交付；任何开放安装之前先保证特权边界。
3. 课表插件与 JSON 规范：使用公开协议实现实际业务并提供正反样例；以单复课、单双周、调课等覆盖接口缺口，不预建无需求的通用扩展点。
4. 跨端集成验收：外部包无需重编宿主即可安装；各端导入相同数据得到相同课程，提醒按本机约束执行；停用与升级不损坏核心笔记。

具体 Step 在相应 Task 获执行指令时建立，不为 pending Task 预建步骤块。该顺序是规划建议，技术可行性尚未验证，不提供虚构工期或复用比例。

## 7. 决策缺口与证据来源

当前最影响架构的未定项是 **iOS 首发分发渠道**：是否计划 App Store，还是先自用开发安装。App Store 4.7 允许符合条件的 HTML5/JavaScript 小程序和插件，但 4.7.2 对向其暴露原生 API、4.7.3 对用户数据共享有额外约束；同时需结合 2.5.2。不能一概声称“iOS 禁止插件”，也不能承诺隔离 WebView 或宿主包装自动满足审核。

官方依据（2026-09-10 查阅，均不等于本项目已实测）：

- [Tauri 移动插件开发](https://v2.tauri.app/develop/plugins/develop-mobile/)：平台原生扩展入口；不是本产品第三方安装运行时。
- [Tauri 通知插件](https://v2.tauri.app/plugin/notification/)：支持平台与通知权限入口，不代替课表调度验收。
- [Apple 本地通知](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/SchedulingandHandlingLocalNotifications.html)：由系统承接已调度的通知。
- [Android Alarm 调度](https://developer.android.com/develop/background-work/services/alarms)：后台及精确定时权限约束。
- [App Store 审核规则 2.5.2 / 4.7](https://developer.apple.com/app-store/review/guidelines/)：动态软件、原生 API 和数据访问规则。

实现、权限对抗样例、schema 校验、平台适配与回归由 AI 承担；用户把控插件开放程度、首发渠道、数据互通范围和体验验收。预期收益是扩展功能独立演进、桌面与手机课程语义一致；尚未产生可证明这些收益的移动安装或通知实测。
